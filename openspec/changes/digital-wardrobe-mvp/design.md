## Key Design Decisions

### 1. 数据存储策略

**决策**: 元数据存 `wx.storage`，图片存本地文件系统。

**理由**:
- `wx.storage` 上限 ~10MB，存图片 base64 很快耗尽
- 本地文件系统无硬性上限（受手机剩余空间限制）
- 图片路径存为字符串，元数据紧凑

**权衡**:
- 换手机数据丢失 → 通过 JSON 导出缓解
- 微信清理缓存可能删图 → 使用 `USER_DATA_PATH` 而非临时路径

### 2. 动态表单渲染

**决策**: 品类定义 `fields` 数组，录入页根据 `fields` 动态渲染表单组件。

**实现**:
```javascript
// 根据 field.type 选择对应组件
const componentMap = {
  text: 'input-field',
  number: 'number-field',
  select: 'select-field',
  date: 'date-field',
  boolean: 'switch-field'
}
```

**理由**: 用户自定义品类时自由定义字段，无需为每个品类写独立页面。

### 3. 状态管理

**决策**: 无全局状态管理库，使用 app.globalData 共享数据 + 页面级 data。

**理由**:
- 小程序规模小，引入 MobX/Redux 过重
- 数据量有限（< 10000 条），全量加载到内存可接受
- 写操作直接持久化，读操作从内存获取

### 4. 图片压缩策略

**决策**: 保存前统一压缩至 1280px / quality 0.7。

**理由**:
- 手机拍照通常 3000-4000px，直接存储浪费空间
- 1280px 在手机屏幕查看足够清晰
- 9 张 × 200KB ≈ 1.8MB/物品，100 物品 ≈ 180MB（可接受）

### 5. 页面路由设计

**决策**: Tab 页（首页/分类/我的）+ 非 Tab 页（录入/详情/编辑/归档）。

**理由**:
- 微信 Tab Bar 限制 2-5 个，核心入口 3 个足够
- 录入/详情为临时页面，不占用 Tab 位置
- 品类管理放在分类 Tab 内，通过子页面进入

## Data Flow

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   User       │     │   Page       │     │   Storage    │
│   Action     │────▶│   Logic      │────▶│   Layer      │
└──────────────┘     └──────────────┘     └──────────────┘
                           │                     │
                           │                     │
                           ▼                     ▼
                     ┌──────────┐         ┌──────────┐
                     │  WXML    │         │ wx.storage│
                     │  Render  │         │ + 文件系统│
                     └──────────┘         └──────────┘

示例: 保存物品
─────────────────────────────────────────────
1. 用户填写表单 → 点击保存
2. Page: 表单验证
3. Page: 图片压缩 + 保存到文件系统
4. Page: 构建 Item 对象
5. Storage: saveItem(item) → wx.storage.sync
6. Page: 更新列表数据
7. Page: navigateBack
```

## UI/UX Guidelines

- **配色**: 暖白主色调 + 品类色标，营造"衣橱"温馨感
- **图片优先**: 物品卡片以图片为主，文字为辅
- **操作流畅**: 左滑物品卡片快捷操作（编辑/处理）
- **空状态**: 每个列表页有引导性空状态设计
- **反馈**: 保存成功 toast，删除二次确认，处理流程分步引导
